# Hub persistence

The Hub uses TypeORM 1.1.2 with its better-sqlite3 driver (12.11.1), typed `EntitySchema` definitions and explicit migrations. Node.js 24.11 or newer is required by this workspace's selected runtime dependencies. Application code uses transaction-scoped managers and never reaches into private TypeORM driver handles. See the [official driver options](https://typeorm.io/docs/drivers/sqlite/) and [schema definitions](https://typeorm.io/docs/entity/separating-entity-definition/).

`openCatalog` initializes only the new platform metadata. `synchronize` and automatic migration-on-initialize are disabled; the explicit pending migrations run in one transaction. The initial migration is additive, preserves NVR tables and leaves `PRAGMA user_version` untouched. It does not attempt a destructive Down migration. Older binaries can continue to ignore the added tables; removing identity history needs an explicit data migration. A newer platform schema marker is rejected without downgrading it.

Physical table and multiword column names use lowercase kebab-case, such as `haus-identity-refs` and `identity-id`. TypeORM quotes these identifiers. SQLite's [identifier quoting rules](https://www.sqlite.org/lang_keywords.html) apply to any manual maintenance query. Legacy NVR names stay on their existing path until an explicit migration updates all consumers.

Identity and readable-address repositories implement the asynchronous core ports. All their reads and writes inside one operation use the same transactional manager. Transactions serialize per database file in a process, including separate DataSources. Their first statement obtains SQLite's writer lock before reading application records, so other processes wait rather than both assigning a canonical ID. The queue propagates each operation's failure while allowing later work after rollback. WAL and a bounded busy timeout are enabled.

The second additive migration adds ownership and receipt metadata. `OrmSessions` persists resource owners, process incarnations, generations and states; `OrmReceipts` persists reservations/outcomes without command arguments. Settled receipts cannot be overwritten by late completion. The platform marker advances atomically to version 2, preserving previous identity and NVR records. These stores contain no credentials. P2.0b wires the services into actual Hub control. Building these source files does not migrate installed data or household services.

## Local credentials

`openVault` uses a separate SQLite file and migration history. Catalog/vault openers reject each other's files before schema migration. `EncryptedVault` implements the internal credential/refresh ports with an explicitly injected 32-byte local key and a provider-validated codec. AES-256-GCM uses fresh 12-byte IVs and 16-byte tags. Authenticated metadata binds home, integration, owner/process, generation, state and attempt. Changing a pending marker or copying ciphertext between resources cannot make an old credential usable. See Node's [authenticated encryption APIs](https://nodejs.org/docs/latest-v24.x/api/crypto.html#class-decipheriv).

Every credential transition takes the catalog ownership guard, then the separate vault transaction. The encrypted Pending marker commits before a provider exchange; competing services see Busy. A crash retains Pending, failed/uncertain exchanges remain blocked, and late results cannot replace a new sign-in or generation. The guard is released before network calls. Only explicit sign-in installs credentials; refreshing cannot silently clear Pending. Errors expose stable codes without crypto/provider details.

`Host` in `apps/hub/src/control` composes the repositories and vault through `@haus/hub/control`. Its caller supplies the home/Hub IDs; a private `local/identity` file pins those IDs before opening the catalog. `local/key` is a persisted 32-byte key, and `local/vault.sqlite` is the separate vault. The POSIX file adapter requires owner-only directory/file permissions, rejects linked private directories/key files, and publishes complete fsynced files without replacing a concurrent writer's file. Missing/corrupt identity or a missing key beside an existing vault requires recovery. Native Windows needs an OS credential/ACL adapter; POSIX permission checks are not simulated there.

Each Host instance gets a fresh process ID. Closing it stops new catalog transactions immediately, drains admitted local guards, then drains/closes the vault and clears its key buffer. A reopened Host does not acquire an old process's grants automatically. The [control composition](control.md) pins provider admission and requires verified local recovery before rebinding a Ready credential. P2.0b.3 must attach actual providers, the OS proof and the control API/bootstrap. There is no ephemeral-key fallback or unverified rebind. Ordinary replication/backups must exclude the entire private directory. Authenticated encryption does not prevent restoring a complete older database/key copy: backup restoration needs fencing and reauthorization rather than silently trusting old rotating tokens.

## Build and evidence

`pnpm --filter @haus/hub build` emits ESM under `dist`; `@haus/hub/storage` is the public compiled entry point. Hub typechecks are included in the root command, and its new TypeScript source/tests are covered by lint/format rules. The container's build stage compiles the Hub, rebuilds the native driver for its target and smoke-opens the deployed ESM entry point. Production dependencies include the native driver; compilers remain in the build stage.

`apps/hub/test/storage/identity.test.ts` exercises real database reopen, atomic rollback, competing DataSources, competing processes through the built export, readable-address conflicts, scope enforcement, additive migration/archive preservation, kebab identifiers, incompatible schema detection and whole-migration rollback. A local `pnpm deploy --legacy --prod` fixture successfully opens the deployed export with better-sqlite3. Linux container execution is not established by that macOS check; Docker's local daemon was unavailable during this increment.

`apps/hub/test/storage/control.test.ts` covers real persisted ownership, interrupted/rejected fencing, simultaneous owners across DataSources/processes, schema upgrade retaining identities, scoped/immutable receipts and Pending/Unknown replay after reopen without a provider call. The guard test proves catalog revocation waits for bounded vault I/O.

`apps/hub/test/storage/vault.test.ts` covers encrypted persistence and state fencing with real SQLite, including inspection of catalog/vault/WAL files for plaintext fixture credentials and the local key. It exercises pending state after reopen, competing stores, revocation during refresh, late replacement, metadata/ciphertext corruption, failure rollback, wrong keys and schema/path rejection. These isolated checks do not establish production key custody or provider acceptance.

`apps/hub/test/storage/host.test.ts` exercises the composed host and compiled Node export, retained mappings/receipts/Pending markers, fresh process identity, wrong/missing/corrupt identity/key handling, private permissions, concurrent key publication and shutdown during local I/O. It does not start the household Hub or connect a provider.
