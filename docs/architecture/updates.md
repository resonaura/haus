# Haus updates

The Updates screen shows the installed version, offered version, release notes and the Hub or client that owns each install. Checking for updates stays read-only. Install requires a Hub admin for Hub and installed App operations. Desktop and mobile use the account and platform permissions of the device running the client.

## Progress and recovery

Each install has an operation ID, target ID, exact artifact identity, phase, revision and optional counters for that phase. A repeated install request for the same target and artifact resumes the existing operation. A different artifact waits until the active operation finishes. Hub and App operations persist through TypeORM and publish progress on the authenticated live channel. The client fetches the operation by ID after reconnect and uses its revision to reject stale events.

1. **Download.** Show `bytes received / total bytes` and the percentage when the transport reports a trustworthy total. Docker pulls can report completed layers and downloaded bytes where available. Use an indeterminate bar for a missing total.
2. **Verify and prepare.** Verify the artifact digest and release provenance before installation. Show the current phase. A percent meter appears only when this phase reports measurable units.
3. **Install and restart.** Show the current phase and keep the operation visible while the target reconnects. A download at 100% changes to _Ready to install_ or _Installing_.
4. **Verify health.** Compare the running version or digest with the requested artifact and observe target-specific health. Show _Installed_ after both checks succeed. On failure, show the specific failed phase and the outcome of rollback, including the running version or a state of unknown health.

Keep cancellation available during download and verification when the transport can cancel safely. The operation owner continues through installation, health verification and rollback across client disconnects. Record the last durable phase before switching versions so recovery can inspect the running artifact and choose the correct next step after an interrupted install.

## Installation owners

- **Hub.** A host-managed installer outside the Hub process verifies the release, records the operation, pins both OCI image digests, takes a consistent catalog backup and starts the replacement using the same mounts and identity. The old container stops before the new one can write. The installer verifies database and media readiness as well as the reported build. Rollback restores the prior image and, when migrations require it, the matching catalog checkpoint. Cluster updates run one Hub at a time, check peer compatibility and active leases, and respect each resource owner. Pause before restarting a Hub whose single-copy workload cannot tolerate the interruption.
- **Installed Apps and plugins.** Run the existing lifecycle on the owning Hub. Resolve an immutable artifact, keep the previous installation for health-check rollback, and expose operation progress from the actual pull and install driver. Bridge claims, volumes, credentials and integration entries follow the existing lifecycle. An update offered in a cluster is installed once by the App owner.
- **Desktop.** The Electron main process verifies and downloads the appropriate signed release for the installed distribution. Send updater events over the existing preload boundary. Show byte progress where available and offer _Restart to install_ after verification. Delegate store-managed and package-manager installations to their platform. On launch, reconcile the previous operation with the installed version. [Electron updates](https://www.electronjs.org/docs/latest/tutorial/updates)
- **Mobile.** Direct native binary releases through the platform store. If Haus adds EAS Update for JavaScript and asset changes, publish by runtime version and channel, show the progress the installer exposes and activate on a controlled reload. Reports about store-owned installation stay at _Open store_ until the app can observe its installed version. [Expo runtime versions](https://docs.expo.dev/eas-update/runtime-versions/)

## Acceptance

Exercise a successful update, unknown download length, duplicate install request, tampered artifact, client disconnect during restart, interrupted installation and failed health check with rollback. A two-Hub fixture must preserve the owner of each exclusive workload and check the running version on the updated Hub before starting the next operation.

## HACS and community repositories

This is the target update flow. The current HA adapter can request an install, but its `updated` response only acknowledges that request. It does not prove activation, health or rollback. Until the operation lifecycle below exists, the UI must not treat that acknowledgement as a completed update.

The Community screen and Updates screen open the same operation. Show HACS itself separately from the repositories it manages. A repository row identifies its owner, installed and offered versions, release notes, compatibility and activation requirement. Visual Tuya/Govee families keep separate component update targets. Updating code preserves integration accounts, device IDs, rooms, bind keys and pairing.

1. **Review.** Resolve a release tag or branch to an immutable commit and artifact digest. Check repository metadata, minimum HA/HACS versions, the actual Kitsune HA version, Python version, platform and dependencies. Surface unknown compatibility; never report it as verified. Identify every loaded entry and exclusive session affected by replacing the code or shared dependencies. Unsupported repository categories remain visible with a reason and no install action.
2. **Prepare.** The runtime owner creates a durable operation and stages the artifact outside the active component directory. Reject traversal, escaping symlinks, unexpected component domains and failed integrity checks. Resolve dependencies into a staged environment and check conflicts against every integration sharing that Python process. Keep the previous code, dependency lock and narrowly scoped compatible storage checkpoint for recovery. This does not require a full HA backup. If a migration cannot be recovered safely, block activation with the exact reason.
3. **Download.** Report actual downloaded bytes and known totals; otherwise use an indeterminate bar. HACS milestone values such as 10/20 are phase notifications, not measured download percentages. Batch progress shows completed repositories out of the selected total, plus the current repository's byte progress. Do not synthesize an overall percentage from unrelated phases.
4. **Activate.** Stop affected owners before replacing code. Python integrations require a fresh process when modules or shared dependencies may remain cached; a reload is sufficient only when the adapter proves it safe. Show the affected integrations and planned interruption before starting. HACS self-update restarts its runtime and is reconciled by the host operation owner, so completion never depends on the process being replaced. In a shared runtime, prepare a compatible batch and restart once; otherwise serialize per repository.
5. **Verify.** Read the running module version/commit, HACS repository state and each previously loaded entry. Check initialization, endpoint identity and new errors; a device that was already offline need not become online. Reauthentication is an explicit outcome, not an invitation to discard credentials or pair again. Mark completion only after the requested artifact is active and the affected runtime is healthy.
6. **Recover.** On failure, fence the candidate before restoring the prior code and dependency environment. Reconcile storage using component-specific recovery; never blindly restore old rotating tokens or replay physical commands. Verify the restored runtime and show the failed phase, rollback outcome and running version. An unknown outcome remains unresolved and blocks a second writer. Client closure or reconnect does not cancel activation or rollback.

The host persists operation state through the neutral Apps update port. HACS wire messages and provider interpretation stay in `packages/ha`; Python lifecycle and artifact activation stay in Kitsune. One queue and lease own each runtime's code/dependency mutation. A remote peer may display progress but cannot independently install the same repository. An uncertain lease prevents takeover until the old installer is fenced.

Bundled integrations such as Starling have an explicit code source. A HACS override requires deliberate adoption of one owner and preserves the current config entry. A Hub update must not overwrite that override; removing it offers the bundled version only after compatibility and identity checks. Never run both copies.

Acceptance adds HACS self-update across process exit, shared-dependency conflict, repository without releases, GitHub rate limiting, downloaded-but-not-activated state, unsafe archive paths, incompatible storage rollback and a mixed-success batch. Verify operation resumption after client/Hub reconnect and preservation of pairing and account state. The upstream [HACS update flow](https://github.com/hacs/documentation/blob/main/source/docs/use/update.md), [update entities](https://hacs.dev/docs/use/entities/update/) and [repository installer](https://github.com/hacs/integration/blob/main/custom_components/hacs/repositories/base.py) inform this design; Haus owns the additional operation and recovery guarantees.
